# AGENTS.md

## Project overview

This is the bilingual Space Cubics corporate website. It is generated by
[Zola](https://www.getzola.org/) and deployed as a static site on Cloudflare
Pages.

- Use the exact Zola version recorded in `ZOLA_VERSION`.
- Japanese is the default language. English content normally uses an `.en.md`
  sibling.
- Do not edit generated files in `public/`.

## Repository organization

- `content/`: Markdown pages, sections, news, job postings, and shortcode calls.
- `templates/base.html`: Site-wide document shell, navigation, main content,
  footer, cookie UI, and scripts.
- `templates/page.html` and `templates/section.html`: Default page and section
  layouts.
- `templates/*.html`: Specialized layouts for products, news, recruitment, and
  other page types.
- `templates/shortcodes/`: Components invoked from Markdown content.
- `templates/partials/`: Components included by templates and shortcodes.
- `templates/macros/`: Shared Tera macros.
- `sass/`: Component styles. `sass/style.scss` controls import order.
- `static/`: Images and browser-side JavaScript.
- `i18n/`: Language-specific strings.
- `functions/`: Cloudflare Workers, including form handling.
- `test/`: Playwright visual regression tests.
- `.github/workflows/`: Build-adjacent checks for links, spelling, formatting,
  commits, and visual regressions.

Changes to a shared template, partial, or shortcode can affect many pages and
both languages. Find every call site and inspect the generated HTML before
assuming a change is local.

## Working on issues

Before implementing an issue:

1. Confirm the behavior still exists on the current main branch.
2. Check related open and closed pull requests. Some open issues describe work
   that was already implemented or attempted in an unmerged PR.
3. Prefer a small, independently testable fix. Split site-wide cleanup issues
   into page- or component-level work.
4. Keep visual changes scoped to the issue and use the existing design system.

Issue #245, "Unify header (h1, h2...) hierarchy", is a cross-cutting
requirement for all work:

- Do not introduce new heading hierarchy problems.
- Improve the hierarchy in templates directly touched by the current fix when
  that improvement is safe and in scope.
- Each substantive page should have one meaningful `h1`, followed by ordered
  `h2` and deeper headings without skipped levels.
- Do not render empty headings.
- Preserve visual styling with classes; do not choose heading levels for their
  browser-default appearance.
- Check every call site before changing a shortcode's heading level.
- Do not turn an unrelated issue into the complete #245 cleanup.

News articles and job descriptions have intentional template-owned headings.
Follow the content guidance in `README.md`: article and job body headings start
at `h3`.

## Content and template conventions

- Use two spaces for indentation, LF line endings, and a final newline, as
  configured in `.editorconfig`.
- Tera does not support ternary expressions. Use explicit `{% if %}` and
  `{% else %}` blocks.
- Content links to local pages must use the `@/` prefix.
- Templates and shortcodes must resolve local links with
  `get_url(path=..., lang=lang)` so Japanese and English URLs remain correct.
- Reuse existing partials and shortcodes instead of duplicating markup.
- Keep JavaScript limited to behavior that cannot reasonably be implemented
  with HTML and CSS.
- Prefix SCSS partials with `_` and import them from `sass/style.scss`.
- Treat SCSS import order as significant because later rules can override
  earlier rules.

## Build and validation

Build the site before and after template, shortcode, content, or SCSS changes:

```sh
zola build
```

For local browsing:

```sh
zola serve
```

If `zola` is not on `PATH`, use the version recorded in `ZOLA_VERSION`
explicitly.

For Playwright tests, build first, then run from `test/`:

```sh
cd test
npm test
```

Playwright starts an HTTP server for `../public`. The visual regression workflow
creates base snapshots dynamically; do not blindly update snapshots to accept
an unintended visual change.

For link-related changes, use the same Lychee configuration as CI:

```sh
lychee --config .lychee.toml --verbose --root-dir "$PWD/public" public/**/*.html
```

Use the smallest relevant validation for the change, but always inspect all
generated pages affected by a shared template or shortcode.
